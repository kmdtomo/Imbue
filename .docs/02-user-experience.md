# ユーザー体験

## 体験の前提

ユーザーはCodexやClaude Codeを普段どおり使う。コードやdiffを直接編集せず、「もっとシンプルに」「そこは既存実装を使って」「一度案を見せて」等の自然言語だけで作業を進めてもよい。学習のための別セッション、必須ラベル付け、事例ごとの承認キューは設けない。プロダクトは作業イベントからデータセットを自動更新し、ユーザーは必要なときだけ内容を確認・訂正する。コードは自然言語へ変換して捨てず、判断が行われた状態と結果を示すEvidenceとして保持する。

本体験は完成形を記述する。初期検証の必須範囲と後段の製品化は[仮説検証と段階的な実装](15-validation-plan.md)に従い分離する。初期検証では少量の標本を本人と照合するが、通常利用に必須ラベル付けや承認キューは追加しない。

## 1. セットアップ

初期はローカルPostgreSQLとDaemonを起動し、次の操作でProjectを初期化する。サービスへのloginは不要とする。

```bash
agent-learning init
```

初期はローカル所有者とプロジェクトを使い、観測対象、リポジトリ、保持期間、除外対象、外部送信可否を設定する。Fireworksを利用する際は利用者がAPI keyを設定し、OS credential storeに保存する。未設定でも収集・Case管理は利用できる。クラウドの認証・チーム共有・課金は後段とする。

セットアップでは、ChatGPT管理認証済みのCodex、非永続な非対話実行、構造化出力、GPT-5.6 Lunaの利用可否を自動確認する。これはSemantic Curatorの必須条件であり、ChatGPT credentialはAgent Learningへ渡さない。条件を満たさない場合は、API key入力へ誘導せず不足項目を表示する。

学習データは対象リポジトリとは別のユーザー管理領域へ保存する。リポジトリへの設定追加、Git追跡、チーム共有は明示的に有効化した場合だけ行う。

## 2. 通常作業の観測

作業中に発生する以下のEventを継続記録する。

- 依頼、仕様、追加要件、修正指示
- 質問、選択肢、承認要求、委任、探索的なやり取り
- AIの応答、計画、利用された指示・Skill
- ファイル参照、ツール操作、コマンドと結果
- コード・設定・文書の変更前後
- テスト、レンダリング、スクリーンショット
- コミット、PR、レビュー、CI、マージ、Revert

記録はユーザーの作業を停止させない。取得できない情報は欠損として明示し、推測で補完しない。

Agent Turnが完了すると、別の非対話Codex RunでLunaによる整形を開始する。このRunはユーザーの作業Taskに表示せず、Caseごとに新規作成して会話履歴を継承しない。Codex/Lunaが一時的に使えない場合は整形Jobだけを保留し、通常作業とEvent収集は継続する。

## 3. Trajectoryの構成

イベント列を、依頼、質問、提案、試行、修正、承認、検証、後続結果などの関係を持つTrajectoryへ自動でまとめる。セッション境界、コミット、タスク切替だけを絶対的な区切りにはせず、対象ファイル、発言参照、目的、ActionIntent、時間、変更の継続性等を根拠にWork Episodeへ関連付ける。

後から結合・分割できるよう、元Eventの識別子と順序は保持する。Sessionが終了または休止してもWork Episodeを成功扱いせず、後日の修正、CI、Review、Revertを同じ仕事へ接続できるようにする。

## 4. Learning Caseの自動生成

修正、追加要件、選好、承認、委任、質問への回答、技術的検証、後日の評価を示すイベントが発生すると、関連するWork EpisodeとDecision PointからLearning Caseを生成・更新する。

ユーザーから見えるデータは、原文・コード・diff・test等のEvidence Data、そこから判断と結果の関係を表したAbstract Experience Data、学習・Eval用途に変換したTraining Projection Dataの三層とする。抽象化後も元Evidenceへ戻れるようにする。

Learning Caseには少なくとも以下を含める。

- 元の依頼と、その時点で与えられていた条件
- 対象となったAIの質問、出力、操作、Tool選択、差分
- ユーザーの修正指示原文
- 修正前後の成果物
- 明示的承認・却下、テスト、CI、レビュー、後続修正等の結果
- 抽出した問題点、修正理由、望ましい判断
- 適用条件、例外、Scope
- Evidence、検証状態、矛盾、欠損
- Memory、Skill、Eval、SFT、DPO、RFT等への適格性

追加要件、選好の絞り込み、誤りの指摘、探索、承認、委任、方針変更、単なる質問を区別する。同一条件でない修正前後を、無条件にPreference pairへ変換しない。後続発言で初めて生まれた要件を、最初から予測すべきだった正解へ変換しない。

自然言語だけで編集が続く場合、各Agent Turn後のartifact snapshotを保存し、`C0 -> C1 -> C2 ...`の収束過程として接続する。明示的に受け入れられた最終artifactは、そのcontextにおける選好Evidenceであり、唯一の正解コードとは扱わない。

## 5. 自動品質管理

承認状態の代わりに、システムが用途別の成立条件を判定する。

- 重複・類似事例の統合候補を検出する。
- 相反する判断を検出し、Scopeや条件で分離する。
- Evidence不足、因果関係不明、要件変更の可能性を記録する。
- Session終了、無反応、単なる会話停止を成功または承認とみなさない。
- 「これでいい」等の明示的承認と、test・CI等の技術的検証を別のOutcome Evidenceとして扱う。
- 質問に回答があった事実だけで、その質問が有益または不要だったと一般化しない。
- Agentの回避可能な修正と、ユーザーが望む探索・承認のための往復を区別する。
- 個人固有、チーム規約、リポジトリ固有、一般判断を分類する。
- 失敗したテストやRevertを、即座に否定例とは断定しない。
- 用途別の必須条件を満たさないProjectionを生成しない。
- PII、秘密情報、外部由来の命令を検出し、隔離または除外する。

根拠の連鎖を構成できないものはRaw Eventに留め、Learning CaseやProjectionとして利用しない。

## 6. 任意の確認と編集

ユーザーは任意の時点で、自然言語または構造化UIから次を行える。

- 「何を学んだか」「この判断の根拠は何か」を尋ねる。
- 元イベントと抽出解釈の差分を見る。
- 解釈、Scope、Evidenceの対応、用途を修正する。
- 一件を複数事例へ分割し、複数事例を統合する。
- 事例を削除、除外、失効させる。
- MemoryからSkillへ移すなど、Projection先を変更する。
- 特定期間、リポジトリ、人物、データ種別を一括訂正する。

編集は次のLearning Case生成にも反映される。ユーザーによる訂正原文と、訂正後の構造化内容を履歴として分けて残す。

## 7. データセットの継続更新

新しいEventは既存のLearning Caseを補強、限定、矛盾、失効させ得る。更新時は元版を上書き消去せず、変更理由と差分を残す。

ユーザーはデータセットについて、件数だけでなく以下を確認できる。

- 新規・更新・矛盾・失効した判断
- Scope別、用途別、検証状態別の分布
- 反復している修正傾向
- 反復しているTool選択、確認、委任、探索、差し戻しの傾向
- 生成規則や抽出モデルの変更による差分
- 特定のDataset Versionを再生成できる状態

## 8. 利用先への変換

Learning Caseと元Evidenceを、目的に応じたTraining Projectionへ変換する。必要なコードcontextは残すが、最終コードだけを自動的に教師targetにしない。

- 明示可能な安定ルールはSkillまたは静的ルール
- 再現可能な失敗と合否条件はEval
- 次回作業で参照価値がある知識はMemoryまたはContext
- 望ましい応答・修正過程の模倣はSFT
- 同一条件で比較できる選好はDPO等のPreference学習
- Task、Tool、Collaboration Policyの候補評価はJudgeまたはOutcome Model
- 実行可能なgraderがある課題はRFT等

即時コンテキスト適用は利用先の一つであり、中核成果ではない。大量の判断を無条件にプロンプトへ入れず、関連性、Scope、競合、機密性を満たしたものだけを渡す。

## 9. 学習

学習は`agent-learning train`の明示実行時だけ開始し、Active Dataset全体のSnapshotからクラウドで行う。初期Base ModelはQwen3.8-27B、実行基盤はFireworks Managed Training、学習方式はLoRAとする。Event収集とLearning Case生成は継続するが、`init`やデータ蓄積だけでは有料Training Jobを開始しない。`--budget`を上級オプションとして提供する。

学習ジョブが完了したモデルはCandidate Modelとする。同一基盤モデルの未学習版、Skill・Context利用版、Current Modelと、未学習Taskで個人適応、機能的正しさ、一般能力の回帰を比較する。互換性・安全性の必須条件を満たさない、または主要能力が許容範囲を超えて低下したCandidateはCurrent Modelへ切り替えない。異なるOutcome軸を一つの品質スコアへ圧縮せず、Dataset Version、条件別の結果、成立・不成立理由を示す。

## 10. 実利用

`agent-learning run`はCurrent ModelをFireworks On-demand Deploymentへ配置または起動し、生成済みProfileでCodexを開始する。DeploymentはScale-to-zeroを標準とし、起動中の応答はModel Gatewayが待機・再試行する。ユーザーは普段のCodex操作のままCurrent Modelを利用し、その後の修正、テスト、Revertを次のデータセット更新へつなげる。

Scopeが不明・競合・対象外の場合は個人化Adapterを使わず、未適応の基盤モデルを利用する。使用Scope、Adapter、選択理由を履歴に残す。評価未完了・件数不足のCandidateは判定不能として扱い、Current Modelへ切り替えない。

Base Model、checkpoint、LoRA、推論用weightはユーザーPCへ保存しない。

通常UXではモデル精度や好みの強さを単一スコアへ数値化せず、「何を学習したか」「どの事例が追加・変更・除外されたか」「どのEvidenceが成立または反証したか」を表示する。仕事のしやすさとコード品質を混同せず、同じ明示指示の反復、回避可能な修正、不要な確認、望まれていない先回り、test・CI・review・revert等を別々に観測する。

## 11. ロールバック

ロールバックは通常フローではなく、問題時の保険として提供する。ユーザーは影響範囲から原因を追跡し、次の単位で戻せる。

- Learning Caseの編集、削除、失効
- Dataset Version
- Projectionと適用ポリシー
- 学習設定とモデル版
- 特定Scopeへの配備

ロールバック後も発生事実は監査履歴として残し、通常利用からは除外する。削除要求がある場合は監査保持より削除ポリシーを優先し、派生物への伝播状況を表示する。

Case訂正・削除後は「データ除外済み」と「配備モデルへの反映完了」を分けて表示する。再学習元の条件と旧モデルのstale・隔離の扱いは[検証計画](15-validation-plan.md#訂正削除後の再学習)に従う。
