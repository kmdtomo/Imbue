# プロダクト定義

## 初期のローカル構成

初期実装は一人のPCで動かす。本文のPlatformは、初期には同じPC上のGo API・Worker・Model Gatewayを指す。PostgreSQL（pgx＋sqlc）とローカルファイルを正本とし、ジョブはPostgreSQLのテーブルで管理する。クラウドホスティング、Object Storage、外部Queue、サービス認証・課金は後段とする。CodexおよびFireworksによる外部AI実行・学習は維持するため、完全オフライン構成ではない。具体的な保存・認証・起動境界は[技術アーキテクチャ](12-technical-architecture.md)を正本とする。


## 一文での定義

AIコーディングエージェントとの日常的な仕事の軌跡から、言語化されていないが選択・修正・承認に現れる判断傾向を根拠付きで抽出し、少量・低ランクの追加学習によって未知の仕事にも定着するかを検証するExperience Learningプロダクト。

## 解決する課題

CodexやClaude Codeを使う実務は、コード生成だけではなく、何を調べるか、どのToolを使うか、どこまで変更するか、いつ質問・確認し、どこから自律的に進めるかという状況依存の判断の連続である。こうした判断基準の多くは本人にも完全には言語化できず、無限の条件分岐をSkillやプロンプトへ書き切ることもできない。

Agentに対する自然言語の修正、追加要件、承認、委任、差し戻しは、その場の成果を改善しても次の仕事へ体系的に継承されない。同じ指摘や不要な確認が繰り返される一方で、会話、質問、Tool実行、コード差分、テスト、後日の結果は分散し、人間とAgentがどのように判断して成果へ到達したかを示す経験として残らない。

既存の長期記憶やRAGは過去情報を再提示でき、Skillはコーディング規約、設計方針、Tool利用、実装・検証Workflowなど、明文化された知識と手順を再実行できる。これらは重要な補完手段だが、細かな判断をすべて外部化すると、実行時のcontext量と検索精度に依存する。修正前後の因果関係や状況ごとの判断境界を、次の仕事へ定着させること自体は保証しない。モデル学習基盤は学習を実行できるが、その前段となる高品質な経験データの生成と管理を解決しない。

## 提供価値

- 普段のAI作業を変えずに、会話、質問、Tool選択、実行、修正、承認、検証、後日の結果を継続的に収集する。
- 明示的なルールだけでなく、反復する仕事の軌跡から状況依存のTask Policy、Tool Policy、Collaboration Policyを学習可能にする。
- コード、diff、testを捨てずに根拠として保持し、観測事実、抽象化された判断、用途別の学習形式を三層に分離する。
- 観測事実とAIによる解釈を分離し、検証可能なLearning Caseを生成する。
- データを自然言語で編集、分割、統合、削除し、変更履歴を保持する。
- 各事例をMemory、Skill、Eval、静的ルール、SFT、DPO、RFT、Judgeなど適切な用途へ変換する。
- データ、生成物、学習済みモデルの関係を追跡し、問題時に戻せるようにする。
- 蓄積された判断を継続的に再利用し、同じ修正、不要な確認、望まれていない先回りを減らしつつ、ユーザーが望む共同探索や承認機会を残す。

中核資産は、可搬性と検証可能性を持つExperience Datasetと個人適応Evalである。基盤モデルが一般的なコーディング能力を既に持つとき、個人差は自律性、調査範囲、リスク許容度、品質基準、実装方針等の少数の判断軸として、小さな重み差分へ圧縮できる可能性がある。これは設計上の前提ではなく検証対象の仮説とする。主要な成果は、この仮説を同一基盤モデルの学習前後と未学習タスクで測定できるデータセット、Eval、チューニングモデルである。Memory、Skill、Context等は比較対象かつ補助的な利用先として扱う。

## 検証の段階

中核仮説を、判断事例の抽出、経験の再利用、追加学習の追加価値、実利用での価値の四段階に分ける。各段階で支持・不支持・判定不能を記録し、抽出の失敗を学習方式の失敗と混同しない。完成形の構想と初期実装の受入範囲は分離する。詳細は[仮説検証と段階的な実装](15-validation-plan.md)を正本とする。

## プロダクト原則

### 日常作業から自動生成する

収集と抽出はイベント駆動で行う。ユーザーに別作業としてのラベル付けや、事例ごとの承認を要求しない。初期検証の標本監査では本人の意図との照合を行い、抽出の正確さ・保留率・有効事例の収集量を測る。監査は通常運用の承認キューとは分離する。

### Sessionを仕事の終了とみなさない

Session、thread、Agent Turn、無反応は収集境界には使えるが、成功、承認、失敗を意味しない。一つの仕事を複数SessionにまたがるWork Episodeとして接続し、後日の修正、検証、Revertで評価を更新できるようにする。

### 往復の最短化を目的にしない

Agentの回避可能な誤りによる修正と、ユーザーが望む探索・確認・承認を区別する。質問数や完了までのTurn数を一律に減らさず、ユーザーが決めたい部分と委任したい部分を状況ごとに学ぶ。

### データセットを正本にする

特定モデルの重み、プロンプト、Memory、Skillを正本にしない。用途別形式は、正規化されたデータから再生成できる派生物として扱う。

### 個人差を低次元の仮説として検証する

「少量のデータとLoRAで個人の判断傾向が定着する」「その傾向が未学習のTaskやrepositoryへ適切に汎化する」と事前に断定しない。同一基盤モデルの未学習版、Skill・Context利用版、チューニング版を比較し、個人適応、一般能力の維持、誤ったScopeへの適用を分けて評価する。

### コードを証拠として保持する

コードを一律に学習データから除外しない。一方、最終コードだけを正解として学習させない。コード、diff、testは判断が生じた状態と結果を接地する証拠として保持し、抽象化された判断と必ず元参照で接続する。学習時は用途に必要な最小限のコードcontextを含め、コード自体を教師にするのは成立根拠がある場合に限る。

### 事実と解釈を混同しない

発言、ツール操作、差分、テスト、Git・CI結果などの観測事実を保存し、修正理由や一般化された判断は別レコードとして管理する。

明示的な「これでいい」はユーザー選好のEvidenceであり、技術的正しさの証明ではない。テスト成功も機能面のEvidenceであり、ユーザーが望む設計や協働方法の証明ではない。「良い反応」を単一の成功ラベルへ圧縮しない。

### 適用範囲を明示する

個人、組織、リポジトリ、領域、ファイル種別、タスク種別などのScopeを、各判断の必須メタデータとして扱う。広い一般化を初期値にしない。

### 用途ごとの適格性を判定する

同じ修正事例を無条件にDPOやSFTへ変換しない。追加要件と否定的評価を区別し、入力条件、比較可能性、検証手段に応じて利用先を決める。

最終artifactを元の依頼への教師にする場合は、後続発言で初めて追加された情報を除外する。その時点で利用不能だった未来情報を過去の正解へ逆流させない。

### 自動化と可逆性を両立する

通常フローは自動で進める。一方、抽出、編集、変換、学習、配備はすべて履歴と根拠を持ち、削除、再生成、ロールバックができるようにする。

### 標準と公開知見を利用する

トレース、会話、ツール呼び出し、SFT、Preference、Eval等の形式は、公開仕様、論文、実績あるOSSを参照する。プロダクト固有設計は、人間とAgentの仕事の軌跡から状況依存の判断を表現するWork Episode、Decision Point、Learning Caseに集中する。

### ベンダーと学習方式を固定しない

Codex、Claude Code等の入力元や、学習・推論サービスを交換可能にする。ファインチューニングを主要経路としつつ、データセット自体は特定providerやmodelへ依存させない。

## 対象

- AIコーディングエージェントを継続利用し、自然言語で成果を修正している個人とチーム
- 実装、設計、UI、テスト、レビュー、調査など、行動と後続結果を観測できる柔軟な作業
- 会話、質問、承認、委任、ツール操作、コード差分、テスト、スクリーンショット、Git、PR、CI、レビューのイベント
- 明示ルールだけでは表現しにくい、状況依存の判断、選好、Tool選択、協働方法

## 非対象

- 過去文書を検索するだけの汎用RAG・個人メモリ
- Skillsやルールを大量生成するだけの仕組み
- 特定のファインチューニングAPIを包むだけのサービス
- 既存コード、コミット、マージを無条件に正解とみなす学習
- コードを一律に捨て、AIが生成した自然言語の抽象化だけを正解とみなす学習
- Session終了、無反応、短いTrajectoryを成功とみなす学習
- 質問や確認を一律に削減し、最短Turnで最終成果へ到達すること
- ユーザーの明示的承認を、技術的正しさや一般的な判断ルールと同一視すること
- 後続の追加要件を、最初のAgent出力の誤りや正解情報へ変換すること
- ユーザーごとのモデル更新だけを正本とし、学習内容を確認できない個人化
- AIの非公開な内部思考を完全に復元すること
- 全用途を一つの学習方式へ統一すること

## 用語

### Event

ユーザー発言、AI応答、ツール実行、ファイル変更、テスト、Git・CI結果など、時刻と発生元を持つ観測事実。

### Trajectory

一つの依頼や作業目的に関係するEventを、順序と因果候補を保ってまとめた作業軌跡。

### Work Episode

一つの仕事の目的に関係するTrajectory、Decision Point、成果物、後続結果をSession境界を越えて接続する開いた単位。無反応やSession終了では成功扱いせず、後日のEventで再開・再評価できる。

### Decision Point

Agentがその時点で利用可能だった情報から、質問、提案、Tool利用、編集、検証、制御返却等の次の行動を選んだ単位。後から追加された要求を当時のcontextへ含めない。

### Learning Case

人間とAgentの仕事上の判断を再利用可能にした正規レコード。対象Decision Point、その時点のcontext、行動、ユーザーの後続発言、成果物、結果、解釈、Scope、根拠の充足状態、用途別適格性を持つ。

### Evidence

Learning Caseの解釈を検証する元発言、差分、ファイル、画像、テスト結果、コミット等への参照。

### Interpretation

Eventから抽出した、問題点、修正理由、望ましい判断、条件、例外。観測事実とは別に版管理する。

### Outcome Evidence

明示的承認・却下、修正、test、CI、review、merge、後続修正、Revert等、行動後に観測された結果。ユーザー選好、機能検証、協働、耐久性を別々に保持し、単一の成功スコアにしない。

### Scope

判断が適用される所有者、組織、プロジェクト、リポジトリ、領域、タスク、技術等の範囲。

### Projection

Learning CaseをMemory、Skill、Eval、静的ルール、SFT、DPO、RFT、Judge等の用途別形式へ変換した派生物。

### Dataset Version

特定時点のLearning Case集合と、その生成規則、除外条件、変換設定を再現可能に固定した版。

### Training Run

Dataset Version、学習設定、基盤モデル、技術的検証、生成モデルを結び付けた一回の学習実行。
