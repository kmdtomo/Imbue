# 原文の経験を中心にした学習データの再設計案

作成日: 2026-09-18。状態: **設計案・未実装**。

この文書は「Lunaがログから判断文を作る」現行経路を見直す提案である。既存の01〜17の設計・実装説明を実装済みの新仕様へ書き換えたものではない。採用時に関連文書とruntimeを一緒に更新する。今回、稼働設定・既存Case・Jobは変更しない。

## 推奨する出発点

経験は元のやり取りに既にある。Lunaが別の自然言語の事例を生成することを、学習データ作成の必須工程から外す。

正本は、原文・順序・発生元を持つ仕事の記録。学習用のサンプルはそこから決定的に切り出す。Lunaを使う場合も、発言と行動の対応先を特定する補助に限定し、原文にない理想回答、一般則、ユーザー像を教師として生成しない。

ただし、これを「最もよく学習できる方式」と断定しない。まずAIによる再記述の少ない基準条件を作り、同じ経験で比較できる設計にする。

## 今回分かった問題

- 旧Jobで同じユーザー発言を根拠にしたCaseが72件生成された。そのうち47件は同じ一発言だけを根拠とする。発言中に複数の要求があるので全件が同義とは限らないが、言い換えによる重複が多数ある。
- 画像などによる44分割に同じ補助発言を再掲し、それぞれでCaseを生成したことが増殖につながった。
- タイトルや判断文の違いが、別の経験のように保存された。
- 既存Caseを毎回すべて渡すため、抽出した文章の蓄積が次の入力を圧迫した。
- hypothesisを任意にする、画像を除く、分割を減らす修正は有効だが、「何を学習サンプルとするか」の問題までは解決していない。

これは事例数を減らすだけの問題ではない。生成文の件数を、経験の量や学習価値として数える設計を変える。

## 10ターンと1サンプルを切り離す

ここでいう1ターンは、ユーザー入力からAgentが制御を返すまで。10個の別会話・セッションを一つにする意味ではない。現行runtimeは同一repository内の未処理完了ターンを合算して起動している。この起動頻度は当面維持可能だが、経験の境界とはしない。

| 単位 | 意味 | 件数を決めるもの |
|---|---|---|
| 処理バッチ | まとめて取り込む範囲 | 頻度・費用。例: 未処理10ターン |
| 仕事の記録（Episode） | 同じ目的に関係する原文と行動の列 | 目的、対象、明示的な継続関係 |
| 学習サンプル | 特定時点の入力と、学習対象にする実際の応答 | 学習方式、情報の充足、教師としての適格条件 |

10ターンからの学習サンプル数は0件・1件・複数件のいずれでもよい。必ず1件に圧縮しない。10ターン終了で途中の仕事を閉じず、次のバッチで継続できる。

同じ10ターンを一つの複数ターン会話として保存・学習することは可能。ただし、そこに含まれる全Agent応答を正例として学習するかは別問題。物理的なJSONLの行数を目的にしない。

## 比較した上での推奨

| 方式 | 利点 | 主な問題 | 今回の位置付け |
|---|---|---|---|
| ログ全文をそのまま学習 | 再記述が少なく流れが残る | 誤応答・ユーザー発言・無関係な操作も教師にし得る。長さ・欠損の問題 | 無条件な本番採用はしない |
| 10ターンをAIで1つの教訓にする | 小さい | 解釈の圧縮、仕事の混合、根拠と条件の喪失 | 既定経路にしない |
| 原文の経験＋学習する応答の明示 | 経緯を保持し、再現と検査ができる | 文脈選択・教師選別の判断は必要 | **最初の基準条件に推奨** |
| 原文にAIの解釈も追加して学習 | 判断を明示できる可能性 | 解釈への依存とバイアス | 基準条件の後の独立した実験 |

AIが文を書かなければバイアスがゼロになるわけではない。収集元、除外条件、切り出し、成功条件、学習の重み付けにも選択が入る。選択を隠さず、規則・参照・除外理由を保存して比較可能にする。

## 新しいデータの流れ

```text
観測ログ（原文、役割、時刻、順序、行動、根拠ID）
  → 機械的な正規化・画像等の除外
  → 原文への参照で保持する仕事の記録
  → 必要な場合だけLunaが対応関係を提案
  → 用途別の条件検査
  → 決定的なサンプル構築（原文の入力・原文の応答・学習対象の指定）
  → 版固定したデータセット
  → 学習と、未学習の仕事での評価
```

可読用のタイトルや説明をUIに付けることは可能。ただし、それを新しい経験や教師文として数えない。初期はユーザーの最初の発言の抜粋等で表示し、Lunaにタイトルを書かせる必要もない。

## 具体例: 記録を残すことと教師にすること

以下は形式を説明する架空の例。実データへ挿入する例ではない。

```text
U1: 設定画面をもっとシンプルにして
A1: 項目数を減らした応答・変更
U2: 項目は残して、見た目だけ整理して
A2: 項目を戻して表示を整理した応答・変更
U3: これでいい
```

記録はU1〜U3をそのまま保持する。「このユーザーは常に機能維持を優先する」という文は生成しない。

Refinement SFTの候補:

```text
入力: U1 → A1 → U2（原文。A2より前に利用できた情報）
教師: A2（実際に観測された応答のうち、適格性を確認した範囲）
採否の根拠: U3（管理用メタデータ。A2生成時の入力には入れない）
```

A1は経緯を理解するための文脈であり、このサンプルでは模倣する正例にしない。ユーザー発言やツール出力も、このAgentを学習するサンプルの出力教師にしない。U3による承認は、この場面での選好を支えるが、技術的正しさを証明しない。実行内容がAgentの報告だけなら、検証済みのコード変更として出力しない。

A2やU3がなければ勝手に補わない。記録は保存し、教師候補の成立状態はpending/insufficientとして残す。

重要な限界: このサンプルは「修正指示を受けて対応する」学習である。U1だけから最初に望ましい行動を選べるようになる保証はない。初回の判断改善と修正対応の改善を別の評価にする。

## 原文からサンプルを構築する契約

### 原文への参照

```ts
type SpanRef = {
  eventId: string;
  jsonPointer: string;     // 例: /content/0/text
  startByte?: number;      // UTF-8境界を検証。省略時はフィールド全体
  endByte?: number;
};

type ExperienceRecord = {
  id: string;
  revision: number;
  repository: string;
  orderedEventIds: string[];
  originConversationIds: string[];
  observationState: "open" | "quiescent" | "reopened";
  linkProposalIds: string[];
};

type TrainingSample = {
  id: string;
  episodeId: string;
  episodeRevision: number;
  projectionVersion: string;
  mode: "refinement_sft" | "observed_action_sft";
  contextRefs: SpanRef[];       // 役割・順序を原本から復元
  targetRefs: SpanRef[];        // 必ず実際のAgent出力を参照
  selectionEvidenceRefs: SpanRef[]; // 後続評価。入力へ逆流させない
  excludedEventIds: string[];
  exclusionRuleIds: string[];
  eligibilityRuleId: string;
  state: "candidate" | "eligible" | "insufficient" | "excluded";
  splitGroupId: string;
  contentHash: string;
};
```

これは内部形式。Providerへ渡す際は実際の文字列とroleに解決する。原文を整形して使う変換は、マスク・役割変換等に限定しversionを固定する。

参照が存在しない、原文と不一致、順序不明、必要なcontext不足、対応するtool schema欠損なら、その投影を保留する。Lunaが書いた文章で埋めない。

### 学習対象の指定

初期は、文脈全体をprompt、対象の実応答をcompletionに分ける形を優先する。prompt部分はloss対象にしない。複数ターンを一行へまとめる場合も、対象外のAgent応答を含めて全assistantへ一律にlossを掛けない。

ユーザー発言を教師にしてユーザー役を予測する学習は、Agentの応答学習とは別実験になるため既定では行わない。

一般的なSFT実装にはcompletionだけ、またはassistantだけにlossを掛ける設定がある。ただし選択的なターン／spanのmaskが実際に適用されたかは、使用trainer・chat template・tokenization後のlabelsで検査する。Fireworks等の利用先が未対応なら、その経路を有効化せず、prompt/completionへ分解する。[TRL SFT Trainer](https://huggingface.co/docs/trl/sft_trainer)

## Lunaの新しい役割

初期の決定的な基準条件では、同一会話の直前応答など、順序だけで構成できる候補を使う。Lunaを必ず毎バッチ実行する設計にしない。離れた発言の対応、同一会話内の話題分岐、明示的に参照された別会話との関係等に必要な場合だけ使う。

Lunaが返すものは、参照と関係候補。本文の再記述を返す必須欄を置かない。

```json
{
  "links": [
    {
      "from_event_id": "U2",
      "to_event_ids": ["A1"],
      "relation": "revision_request",
      "supporting_event_ids": ["U2", "A1"],
      "state": "proposed"
    }
  ],
  "unresolved_event_ids": []
}
```

実際には許可されたIDだけを受理する。relationの候補はrevision_request / added_requirement / explicit_acceptance / continuation / topic_change / unknown程度から始める。分類も推論であり、保存しただけでは教師適格性を意味しない。曖昧ならunknownにし、広い好みや性格を生成しない。

ユーザー投稿内の引用は「ユーザーがその文字列を投稿した」事実である。引用された他Agentの発言を、そのまま本人の独立した評価と認定しない。

Lunaには未処理の範囲と関連する元ログ・未解決リンクを渡す。既存Case全文の束は渡さない。入力上限を超えたら関係を保って分割し、入力欠損を明示する。再掲contextと新規観測を区別する。

## 出力を何件作るか

サンプル数の目標をLunaへ与えない。機械処理が原文の対象応答ごとに候補を構築し、用途別条件を検査する。

一つの仕事に複数の学習可能な応答がある場合は複数サンプルになり得る。同じ仕事を複数サンプルにすること自体を独立経験の増加とは数えず、episode単位で件数・重みを管理する。件数を増やすための言い換えや同義の複製をしない。

同じターンを異なるcontext窓で切る実験をする場合、variantを明示し、同じtargetの複数窓を既定datasetへ重複投入しない。

## 教師の採否とバイアス

すべての実応答が正解ではない。初期の保守的な候補では、対象が特定できる明示的承認、本人が選択した候補などの根拠を保存する。実行結果が必要な用途では別に検証根拠が必要。

Lunaの「良さそう」という判定、無反応、最終応答、短い会話を採否根拠にしない。通常の利用に毎件の人手承認は要求しないが、実験用に小さな標本を本人と照合する。

明示的承認に限定すると、承認が言語化されやすい仕事へ偏り、利用できる量が減る。この偏りも記録する。根拠の薄いログは捨てず、原文として保管する。適格条件を緩める場合は別の実験条件として比較する。

「最初からユーザーに合う判断」を学ぶ用途では、その時点で利用可能な情報からの実応答を対象にする。修正後の回答を修正前のpromptへ付け替えない。根拠が不足するなら、その目的の教師はまだ得られていないと扱う。

DPOは同じ入力条件に対する比較候補と選好の根拠がある場合に限定する。修正指示の追加でcontextが変わったA1/A2を、そのままchosen/rejectedにしない。この初期案ではDPO用の理想回答生成は行わない。[DPO原論文](https://arxiv.org/abs/2305.18290)

## 重複と分割を機械的に管理する

- Raw Eventの同一性は既存のEvidence IDで判定する。
- 関係候補はfrom/to/typeの正規化した集合で同一性を持ち、再実行で同じリンクを増やさない。
- サンプルはscope、対象応答の参照、mode、projection version、確定したcontext参照で再現可能なIDを作る。
- 同じtargetのcontext違いはvariantとして記録し、snapshotごとに採用する一つを明示する。
- 生成したタイトルや文面は同一性の判定に使わない。
- 同じ発言内の異なるspanや異なる実行は、同じ根拠IDだからといって無条件に統合しない。
- 関連仕事や同じ対象応答の派生サンプルはtrain/development/testに跨がせない。後日リンクが分かった場合は該当評価を無効化して再分割する。

## 入力の量を制御する

画像本体は学習入力から除外する。コマンド全文も引き続き既定の入力には入れない。原本は保存する。

会話の中だけで復元できる協働判断・修正対応を最初の対象にする。見えていない実行状態に依存するコードやツール操作を、会話だけから教師にしない。将来、必要な実行事実を使う場合は別の明示的な投影仕様として追加する。

一回の10ターンの処理を小さくするために、Lunaが先に会話を要約する工程は置かない。重複データを再送せず、関連する原文の参照範囲を限定し、既存の全件Caseの再投入を廃止する。

ここでの除外は学習材料を減らす選択であり、完全な原文利用とは呼ばない。除外箇所に依存するサンプルは保留する。

## 最初の実験

まず学習ジョブを回す前に、現在のログから異なる種類の仕事を少量取り、原文中心のサンプルをオフラインで構築する。固定10ターン窓、原文の仕事単位、Lunaの対応付けありを同じ元データで比較できるようにする。

初回の監査は「本人の嗜好をうまく文章化したか」ではなく、次を調べる。

- 入力時点にない未来情報が混ざっていないか。
- 対象応答が原文と一致するか。
- 差し戻された応答を正例として学習していないか。
- 依頼と修正の対応先を誤っていないか。
- 画像・実行記録の欠損を推測で埋めていないか。
- 同じ経験を重複して数えていないか。
- 採用だけでなく、保留・除外にも不適切な偏りがないか。

学習を行う段階では、同じ基盤モデル・同じ経験集合で、未学習、原文の経験をContextで渡す、原文からのSFTを比較する。さらにLunaの対応付けを使う版の追加価値を比較する。生成した解釈文の学習は、採用するなら独立した後段の実験とし、既定datasetに混ぜない。

件数だけで比較せず、元Episodeの数、学習対象token数、計算予算を記録する。長い一つの仕事や、サンプルへ切り出しやすい仕事の過大な寄与も確認する。

改善指標は、未学習の仕事に対する初回判断の一致、修正対応、不要な確認、必要な確認の維持、技術的回帰、Scope外への誤適用を分離する。最小評価件数・予算・採用基準はpilotで見積もり、最終評価の前に固定する。今回の設計だけではモデル性能は未検証。

## 現行実装からの移行

1. Evidence収集・redaction・ID・元ログ保存を維持する。既存Caseはlegacyな解釈として保存し、新datasetの教師から既定で除外する。削除も自然言語での再要約も不要。
2. 新しいjobsの種類を追加し、既存Case生成のcursorと新しい正規化・投影のcursorを分ける。同じ取り込み済みイベントを新経路で再処理できるようにする。
3. ExperienceRecord、LinkProposal、TrainingSample、dataset snapshotの保存と参照検証を追加する。失敗は元範囲を保持し、成功時のみ新経路の処理位置を更新する。
4. Lunaなしの決定的なサンプル構築を先に実装し、元ログと並べて確認するUI・export previewを作る。role、tokenization、loss maskまで検査する。
5. 必要な対応付けだけLunaへ依頼する。現在のChanges/experience/hypothesisを教師作成の中心契約から外す。過去Caseの束を新入力へ流さない。
6. 同じ生ログで比較検証した後、新経路へ切り替える。旧quarantined Jobは旧方式へ単にretryせず、元Evidenceの範囲から新経路へ明示的に再投入する。旧履歴は保持する。

この文書作成時点で上記移行は未実施。現在の収集・整形サービスは従来どおり稼働している。

## 受入条件

- 10ターンから0件・1件・複数件を構成でき、件数を強制しない。
- 原文からtargetを完全に復元でき、Lunaによる新しい教師文が混入しない。
- 前の誤応答はcontextには残せるが、そのサンプルのloss対象にはならない。
- 後続の承認等は選別用メタデータへ分離し、過去の入力へ混入しない。
- 同一ログの再送、再分割、retryで対象応答の学習回数を水増ししない。
- バッチ境界で仕事を成功扱い・終了扱いにしない。
- モデル・provider・chat templateが変わっても原文参照から再構築できる。
- 生ログ量、独立した仕事数、候補数、採用数、保留数、対象token数を別々に表示する。

## 公開資料と設計判断の区別

SWE-smithはAgentの実行軌跡を含む学習データとモデルを公開しており、教訓文への要約だけが学習形式ではないことの参考になる。ただし、タスクを合成したソフトウェア修正の研究であり、個人の会話ログから嗜好を学ぶImbueの効果や最適な単位を証明するものではない。[SWE-smith](https://arxiv.org/abs/2504.21798)

TRLのloss設定、DPOの比較形式は実装上の参考。本提案の10ターン起動、Lunaの役割制限、原文参照を正本にする設計は、Imbueの要件と実ログでの失敗に基づく提案であり、論文が保証する最適解ではない。
